一、 理论与指标定义的 3 个逻辑硬伤（最危险，必须优先改）

⚬     硬伤 1：表 5-1 中 Precision = 1.0 掉进了你自己在批驳的“自证循环”
    ⚬         问题所在：在受控主体的 24 个过渡上，文件级 coverage_only 选了 54 次用例，报了 Precision = 1.0；而 graph-selection 只选了它的真子集（16 次用例），居然也报了 Precision = 1.0。如果 16 次就已经包含了全部真正受影响的测试（SafetyEmp = 1.0），那多选出来的 38 次测试必然是未受影响的误选，coverage_only 的真实精度绝不可能是 1.0。
    ⚬         根因诊断：你在 §4.8 中将 Precision 定义为 |Sel ∩ Affected| / |Sel|，这里的 Affected 用的是文件级覆盖 Oracle，而不是非循环的结果差异 Oracle A_obs。由于在自然 diff 下只有 4 个过渡存在非空的 A_obs，你用覆盖 Oracle 算 Precision，却在摘要和 §5.1.1 第 4 点中宣称“选中的每条测试都真正受影响（无噪声）”，这在数学上是自相矛盾的。
    ⚬         修复办法：严格区分 Precision_cov（相对覆盖影响域）和 Precision_emp（在 A_obs ≠ ∅ 的过渡上相对真实结果差异），并撤回“54 次和 16 次都零误选”的绝对化表述。
⚬     硬伤 2：状态依赖闭包公式（§3.5）同时违反了“无泄漏纪律”和因果方向
    ⚬         问题所在：§3.5 给出的闭包公式写成了 SelClosed = Sel ∪ { t : ∃ s ∈ (Sel ∩ A*), t 与 s 在 ⤳ 关系下共享资源 }。
    ⚬         根因诊断：这里有两个严重错误。第一，在选择阶段尚未运行 V_new，算法根本不可能提前知道金标准 A*，把 A* 写进选择公式直接违反了 §3.1 的无信息泄漏纪律。第二，对照表 5-3 的实测场景（Δ = {src/dashboard.js}，生产者 A 写共享状态但未触达 Δ，消费者 B 触达 Δ 被选入 Sel），全量运行 [A, B] 在新旧版本都是 pass（此时 A* = ∅）；之所以子集重跑翻转为 fail，是因为跑消费者 t ∈ Sel（即 B）时漏掉了它的前置状态生产者 s（即 s ⤳ t 的 A）。按你现在的公式，当 A* = ∅ 时 SelClosed 根本不会把 A 加进来。
    ⚬         修复办法：将公式修正为基于静态/历史足迹的前向与后向可达闭包（不依赖 A*）：凡是 t ∈ Sel 所读取共享状态的上游写入者 s（保证前置环境保真），以及 s ∈ Sel 写入共享状态后的下游读取者 t（防止修改写入逻辑污染下游），一并纳入 SelClosed。
⚬     硬伤 3：命题 1“仅依赖动态 executes 边保证召回”与 references 静态归因矛盾
    ⚬         问题所在：§3.2 和 §3.4 声称“executes（动态）边是唯一参与召回承诺的边；references / 路由级 / 文件级只做精度细化与保守兜底”。
    ⚬         根因诊断：在四层归因中，当模块顶层常量或变量发生改动时，你并没有回退到文件级全选，而是用静态 AST 的 references 边只选“读取了该变量的函数所对应的测试”。你在 §6 中提到“无 reader 时保守回退文件级”，但如果某个被导出的变量在同文件内有 1 个静态 reader（不触发无 reader 回退），同时在跨文件或通过动态属性访问有另 1 个未建边的 reader，你的选择器就只会选前者而漏选后者。这意味着召回保证实际上强依赖于 references 静态分析的完备性，而不仅仅依赖动态 executes 边。
    ⚬         修复办法：在 §3.4 诚实修改命题条件——明确指出当启用 references 和 route-diff 裁剪文件级覆盖集时，条件安全假设 (H2/H3) 需同步扩展为“模块内静态引用边完备（对 export 导出变量或动态属性访问自动回退文件级）”。

二、 实验设计的公平性与口径一致性问题（3 处）

⚬     问题 4：RQ2 的无 diff 基线（nodiff）过弱，容易被质疑为“稻草人基线（Strawman Baseline）”
    ⚬         问题所在：根据 §3.7(3)，diff 臂拿到了新增路由名和完整的路由源码，而 nodiff 基线“只给应用名并允许自选有意义的用户流程”，连目标路由列表或应用页面源码都没给。
    ⚬         审稿人质疑：只给 LLM 一个项目名字（比如受控应用名），不给任何 DOM 结构或源码，模型当然只能瞎猜定位器和 URL，导致可执行率为 0.0（表 5-5）。这并不能证明是“缺乏 diff 约束”导致失败，而仅仅是因为“没给源码上下文”。
    ⚬         修复办法：如果时间允许，补一个更公平的消融基线 code_no_diff（给 V_new 完整页面源码或路由表，但不告诉模型哪部分是本次 diff 新增的）；如果不补实验，必须在 §3.7 和 §6 中把 nodiff 重新定义为“零上下文盲生下界”，避免过度拔高对比结论。
⚬     问题 5：真实项目 actual-budget 出现“34 条”与“62 条”两套打架的数据，且表 5-4 缺席核心方法
    ⚬         问题所在：在 §5.1.2（表 5-4）和 §5.4（表 5-9）中，actual-budget（actual_desktop）的全量测试数是 34 个用例（6 个 spec），T_full = 110.84s；但在 §5.2 和 §5.4 前半段，同一个 actual-budget 突然变成了 62 个 E2E 测试，T_full = 168s。更关键的是，既然 graph-selection（四层归因）已经扶正为本文的核心选择方法，为什么表 5-4（真实项目 14 个连续 commit replay）里只跑了文件级的 coverage_only / dual（Reduction 仅 0.111 和 0.0），却没有跑 graph-selection？
    ⚬         修复办法：第一，在 §4.9 明确交代 actual-budget 两个版本/套件规模（34 vs 62）的差异原因（例如不同 commit 窗口或 spec 过滤范围）；第二，把 graph-selection 在 actual-budget（9 个过渡）和 mermaid-live-editor（5 个过渡）上的重放结果补进表 5-4——哪怕在 mermaid 单页强耦合应用上函数级归因依然缩减有限，也比核心方法在真实多 commit 主表中“缺席”要强得多。
⚬     问题 6：受控主体排除 src/main.js 的实现描述与实验结论前后矛盾
    ⚬         问题所在：§4.4 第 2 步明确写着“受控主体只保留 src/ 下的应用文件（排除 src/main.js）”；但 §5.1.1 和 §6 又说文件级 coverage_only 在 5 个“加路由”过渡上全选了 6 条测试，原因是“main.js 路由器被每条测试在导航时真实执行”。如果 src/main.js 在解析 diff 时就已经被排除了，文件级覆盖怎么会因为改了 main.js 路由表而全选 6 条测试？
    ⚬         修复办法：核对 run_rq1.mjs 和 rq1_graph.json 的真实代码逻辑——大概率早期为了防全选排除过 main.js，后来做路由实验时又放开了。务必把 §4.4 的文字改回与落盘数据一致的真实逻辑。

三、 原型实现章节（第 4 章）与方法/实验的“两张皮”断层（2 处）

⚬     问题 7：第 4 章和附录 A.2 停留在旧版“文件级架构”，新核心模块的工程实现集体失踪
    ⚬         问题所在：你在第 3 章和第 5 章把 test-code graph 四层归因（函数级 executes、变量级 references、route-diff、detectGaps、asserts 断点诊断、以及 §5.4 提到的 tree-sitter 静态图构建）作为核心贡献；但翻到第 4 章（§4.1–§4.4），全文写的依然是旧版文件级代码：coverageMap.mjs 只压成“测试 → 文件集合”，selector.mjs 只有文件级 selectByCoverage，gap.mjs 还是集合求差，连附录 A.2 的复现命令里都没有生成 out/rq1_graph.json 和 out/rq2_rq3_graph.md 的脚本命令。
    ⚬         修复办法：重写 §4.2 和 §4.3 的对应段落，补齐：(1) CDP V8 覆盖率是如何从字节偏移量（startOffset/endOffset）精确映射到具名函数（executes 边）并处理 Vite/bundler 源码映射的；(2) tree-sitter / TypeScript AST 是如何抽取模块变量 references 和路由表的；(3) 在附录 A.2 补上跑图选择器的复现命令。
⚬     问题 8：“增量维护”只停留在第 3.2 节的伪代码，RQ4 实测却是全量重建且漏算了动态覆盖更新成本
    ⚬         问题所在：§3.2 用算法伪代码和摊销复杂度重点论证了映射器的增量维护（只重插桩 T_touch、只重抽变更文件的静态边）；但到了 §5.4 实测 actual-budget 的 T_select ≈ 9.1s 时，实际跑的却是“tree-sitter 构建 1968 文件静态图 + 选择器”（每次全量扫 1968 个文件）。同时，§3.6 定义 T_select = T_mapper_update + T_diff_analyze + T_select_compute，在连续 CI 提交中，跑完选中测试后写回/更新映射器也是有开销的，且 §4.2(4) 中 statedep.mjs 的共享状态读写足迹（特别是表 5-3 的后端持久化状态）到底是自动插桩采集还是手工配置声明的，文中完全没交代。
    ⚬         修复办法：(1) 在 §5.4 明确说明 9.1s 是冷启动全量静态分析的上界开销（若做增量缓存只解析 diff 文件可降至亚秒级）；(2) 在 §4.2(4) 坦诚说明 statedep.mjs 当前如何获取读写足迹（比如对 localStorage/cookie 通过运行时 Hook 自动采集，对后端状态通过声明式注解或 API 路由读写标签标注），避免评委追问“你怎么自动知道后端数据库哪个表被读写了”时卡壳。
