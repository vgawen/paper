## 0.1 一句话原则

**不跑测试，只读发放给你的材料，做语义判断。**

自动指标测的是“行为上有没有差异”；你要判的是“语义上是不是在验证这次变更 / 这次失效属于哪种过时”。两件事回答的不是同一个问题。人工盲评是对自动判据的**构念效度校准**，不是把测试再跑一遍。

## 1. 背景：你分别在判什么

### 1.1 RQ2：一条生成的测试，到底有没有验证这次变更

RQ2 的研究对象是**真实项目上的 30 条生成测试**：

| 项目 | 内容 |
|---|---|
| 变更上下文 | 15 个真实变更：actual-budget 14 个、mermaid-live-editor 1 个 |
| 每个上下文 | 生成 2 条测试：1 条来自 diff 约束臂（生成时使用本次变更信号），1 条来自 nodiff 臂（不使用变更信号，作为对照） |
| 总数 | 15 × 2 = 30 条 |
| 两条测试的关系 | 共享同一个变更；生成条件不同；**臂别对你隐藏** |
| 你要回答 | 这一条 spec 是否真的打开应用、操作或断言了这次变更引入/改变的具体 UI/行为 |

注意：同一条变更会出现两次，两次的 spec 可能完全不同。你不需要猜哪条来自哪个臂，也不允许去猜；你只需要按同一条判据，分别判断每一条 spec。

**为什么不能只看自动语义有效率？**

RQ2 的自动语义有效率定义为：**可执行 ∧ 版本敏感 ∧ 杀掉至少 1 个注入变异**。它是一个可操作代理，不是语义金标准：

| 自动指标 | 能测到什么 | 可能误判什么 |
|---|---|---|
| 可执行 | 测试能不能跑 | 语义很好的测试可能因环境、时序、fixture 问题单次失败（假阴性） |
| 版本敏感 | 测试在旧版本失败、在新版本通过 | 旧版本失败可能只是旧页面/旧路由不可用，不是验证了变更（假阳性） |
| 变异杀伤 | 测试能不能发现注入的 testId 改名、可见文本改动 | 只断言元素存在就能杀，不等于验证了新行为；验证逻辑变化的测试反而可能杀不掉（假阴性） |

除此之外，自动 RQ2 实验是在**受控主体的 3 个缺口**上做的。这 30 条来自两个真实项目，补的正是**真实项目上的外部效度**：自动指标在受控小样本上成立，不代表在真实工程里也成立。

所以你要判的不是“这条测试能不能跑”，而是“它是不是真的触达了这次变更”。这就是自动指标覆盖不到、必须由人来定的部分。

### 1.2 RQ3：一条断掉的旧测试，为什么断

RQ3 使用的是 ReproBreak 数据集：

| 项目 | 内容 |
|---|---|
| 原始断裂 | 449 条执行验证过的 locator 断裂 |
| 无泄漏过滤 | 跳过 35 条会泄露新定位器的样本，414 条进入评估 |
| 抽样 | 4 个真实仓库各抽 10 条，共 40 条 |
| 抽样方式 | **每仓等额**，不是按池比例，也不是按标签分层 |
| 你要回答 | 这一条断裂属于哪种过时 |

每一条断裂都已经确认在旧版本上真实失败。你不需要判断“它断没断”，而需要判断“它为什么断”。这直接决定修复政策：

| 标签 | 含义 | 对应修复政策 |
|---|---|---|
| `STRUCTURAL_ONLY` | 测试意图不变；只是 locator、DOM 层级、class/id、文案锚点、测试 API 或框架迁移/格式变了 | 可以自动做语义定位重写 |
| `EXPECTATION_CHANGE` | 测试要验证的业务结果/断言目标发生实质变化；旧断言还在检查旧行为 | 需要改断言语义，通常要人工/业务确认 |
| `SUSPECTED_REGRESSION` | 无法排除新版本真的回归；看不出是测试老了还是应用坏了 | 不应自动改写采纳；保守排除 |

**为什么必须人工分诊？**

执行结果只能证明“这条测试断了”，不能证明“是测试写法过时、业务预期变了、还是应用真回归”。这三个判断对应完全不同的修复动作：

- 把 `SUSPECTED_REGRESSION` 误判成 `STRUCTURAL_ONLY`，可能把真实缺陷当成测试过时，自动改写后掩盖 bug。
- 把 `STRUCTURAL_ONLY` 误判成 `SUSPECTED_REGRESSION`，会放弃本来可以自动修复的用例。
- `EXPECTATION_CHANGE` 则需要改断言目标，不能只换 locator。

因此 RQ3 的人工盲评不是“复核自动标签”，而是给三分类分诊提供独立的人类判断。

## 2. 为什么必须盲评

### 2.1 盲的是答案，不是输入

盲评不是让你“看不到变更”。恰恰相反，你必须看到足够的变更和测试上下文，才能判。

- **你可以看到的输入**：应用源码 diff、旧测试、commit 说明、应用改动文件列表、遮蔽后的断言变化。
- **你不能看到的答案**：这条 spec 属于哪个臂、第一列判了什么、自动指标是多少、RQ3 的 `new_locator` 和新测试。

**输入要给足，答案要藏住。** 如果输入不足，你判的是另一个问题；如果答案泄露，κ 就没有意义。

### 2.2 为什么需要第二个人

如果只有一个人标注，标签看起来“很一致”，你无法区分两件事：

1. 判据本身很清楚，换个人也会这么判；
2. 判据其实有歧义，只是这个人手松/手紧，或者一直按同一个默认值填。

第二个人和 κ 的作用，就是把“判据清楚”和“个人尺度”分开。只有一个人时，你无法证明自己的判断可复现。

### 2.3 第一列不是金标

第一列是 **LLM 依据同一份判据做的预标注**，不是独立人类金标。它可能有自己的系统性偏好，也可能在少数类上错得很一致。

因此：

- κ 衡量的是**预标注-人工一致性**，不是“谁对”，也不是 human-human κ。
- 你的任务是独立判断，不是去猜第一列会怎么判，更不是去迎合它。

### 2.4 Cohen's κ 是什么、怎么读

κ 是“扣掉随机一致之后，还剩下多少一致”：

```text
κ = (Po − Pe) / (1 − Pe)
```

- `Po`：两列实际一致的比例。
- `Pe`：如果两边都按各自的标签分布随机填，期望的一致比例。
- `κ`：扣掉 `Pe` 后的真实一致度。

为什么不能只看 `Po`？因为当某一类占绝大多数时，两边即使都在“随大流”，`Po` 也会很高。κ 会把这个“随大流”的部分扣掉。

但 κ 对**偏斜分布**很敏感：40 条里如果绝大多数都是同一类，`Pe` 会很高，`Po` 看起来不错，κ 却可能很低；反过来，小样本里 κ 也不稳定。所以报告时必须同时给出：

- `n`（参与计算的样本数）；
- `Po` 和 `Pe`；
- 两列的**混淆矩阵**（谁判成什么、分歧落在哪一类）；
- 分歧条目的具体案例。

当前评分脚本的 JSON 会输出 κ、`Po`、`Pe`、`n`，但**不输出混淆矩阵，也不计算置信区间**；混淆矩阵需要从两列交叉表手工整理。30/40 条是小样本，论文里不要写“95% CI”。

### 2.5 κ 低不是失败

κ 低不等于标注做错了。它可能说明：

- 判据在某些类型上确实有歧义；
- 自动代理在某些类型上系统性误判；
- 某一类样本太少，统计本身不稳定。

这些分歧恰恰是论文“威胁与局限”最有价值的材料。**不要为了让 κ 好看而改标签。** 你的独立判断比一个漂亮的一致率更重要。

### 2.6 正式列口径：三次重复多数票

LLM 预标注列固定使用 `deepseek-v4-flash`、`temperature=0`，但 `temperature=0` **不保证确定性**：同一材料、同一 prompt 重复调用仍可能给出不同标签。因此正式列按以下口径固定：

- 每个条件重复运行 **3 次**（含首次），逐条取**三次多数票**作为该条的正式预标注；
- 必须同时报告逐条一致率：**3/3、2/3、1/3** 各多少条，以及所有不稳定条目的取值序列；
- 不能只报某一单次运行的分布；单次运行只作为运行记录保留；
- 多数票出现平票（三条三种标签）时，标为 `TIE`，不得强行归入某一类，须提交人工判断；
- 报告时同时给出重复次数与调用总量（RQ2 30 条 + RQ3 40 条 × 3 次 = 420 次逐条调用）。

当前实测：140 条中 137 条 3/3、3 条 2/3、0 条 1/3；不稳定条目为 `rq2_023`、`rq2_019`、`rb040`。详见 `experiments/out/repeats/variance_report.md`。

## 3. RQ2：怎么判

### 3.1 你会看到什么

当前版式（已生成）：

| 字段 | 内容 | 用途 |
|---|---|---|
| 变更文件 `gap_file` | 本次改的是哪个文件/组件 | 定位变更 |
| 变更上下文 `route` | `项目:路径`，只是定位信息，**不是页面功能说明** | 定位项目和文件 |
| 应用源码 diff | 该文件在变更前后的 diff hunk，**只含应用源码，排除测试** | 判断元素是否对应变更、变更不存在时是否会失败 |
| `spec` | 生成出来的测试代码全文 | 判断是否真的打开应用、断言是否具体 |
| 判定行 | `annotator2_yn=___` | 你填 `y` / `n` |

当前盲表已包含 `gap_file`、`route`、应用源码 diff 和 `spec`。如果某条看不到应用 diff，说明该变更没有可展示的应用源码改动，或抓取失败（工作表内会写明），此时停下来问协调者，不要凭文件名猜“变更大概是什么”。

### 3.2 问四个问题

四个问题都过，才填 `y`：

| 问题 | 判断依据 | 倾向 |
|---|---|---|
| 它有没有真的打开应用？还是 `page.setContent(...)` 自己造了假 DOM？ | `spec` | `setContent` → `n` |
| 它操作/断言的元素，和 `gap_file` 里的变更对得上吗？ | 应用 diff + `spec` | 对不上 → `n` |
| 断言是不是具体到“变更后的结果”？还是只断言 body/页面/通用 header 可见？ | 应用 diff + `spec` | 空泛 → `n` |
| 如果这次变更不存在，这条测试会不会失败？ | 应用 diff + `spec` | 不会 → `n` |

如果应用 diff 缺失，第 2、3、4 问都答不实。此时不要用“看起来挺具体”来代替，应该停下来，向协调者确认材料是否完整。

### 3.3 典型判断

- `page.setContent('<div>...')` + 一堆 `locator('cell')` → `n`：测的是自己造的假页面，不是真实应用。
- `page.goto('/')` + `expect(page.locator('body')).toBeVisible()` → `n`：通用 smoke。
- `page.goto('/budget')` + 点击这次新增的按钮 + 断言新增的行/文本 → `y`：打开了真实页面，动作和断言都指向变更。
- 用项目 fixture（`import { test, expect } from './fixtures'`）并操作真实组件选择器，通常说明打开了应用；但仍要确认它触达的是 `gap_file` 对应的变更，而不是随便点一个老按钮。
- 断言元素存在、但没有任何与“变更后行为”相关的检查 → 倾向 `n`。

### 3.4 常见误判

- 把“能运行”当成“语义有效”。能运行只说明可执行，不说明它在验证变更。
- 看到 `getByTestId` / `getByText` 就判 `y`。要看这个 testId/text 是否就是本次变更引入或改动的锚点。
- 因为测试代码很长就判 `y`。长代码不等于相关，可能只是把老流程又走了一遍。
- 看到 `route` 里有页面名，就假设测试一定到了那个页面。要以 `spec` 里的实际导航和断言为准。

### 3.5 填写

- 只填小写 `y` 或 `n`。
- 不要修改 `case_id`、字段名、节顺序、代码块。
- `final` 留空，它只由第三人在两列不一致时填写。
- 拿不准时，可以在“备注”里写你缺哪条信息，但不要用备注代替标签。

## 4. RQ3：怎么判

### 4.1 你会看到什么

当前版式（已生成）：

| 字段 | 内容 | 用途 |
|---|---|---|
| 测试文件 + 行号 | 旧测试在哪、断点在哪 | 定位 |
| `old_locator` | 断掉的是哪个定位器 | 判断断的是写法还是语义 |
| 完整旧测试块 | 断点所在的完整 `it` 块，至少包含旧断言 | 判断旧测试想验证什么 |
| `Commit` 主题 | 提交标题 | 判断是加功能、修 bug、重构、迁移还是改业务 |
| `Commit 说明` | 提交正文；若该 commit 本身无正文，会明确写“（该 commit 无正文）” | 补充变动性质；不是决定性证据 |
| 完整应用改动文件列表 | 应用源码改了哪些文件（不截断） | 判断改动范围 |
| 应用源码 diff | 应用代码具体怎么改 | 判断应用行为/结构是否变 |
| 断言级测试 diff（机械路径已遮蔽，语义锚可见） | 只展示断言的增删；机械寻址路径替换为 `<LOCATOR_REDACTED>`，role/name/文案/断言值保留 | 判断断言目标/业务预期是否变 |
| 判定行 | `human2=___` | 你填三个标签之一 |

当前盲表已包含上述全部字段。完整旧测试块由 `it/test` 括号配对提取；极少数文件无法稳定配对时会退化为断点附近窗口，该条会在工作表内标注“旧测试块退化为窗口”。如果旧测试块里看不到断言，也会标注并补断点窗口。遇到这些标注，先判断是否仍能读懂旧测试意图；读不懂就停下来问协调者，不要猜。

### 4.2 三个标签

- `STRUCTURAL_ONLY`：测试意图不变；只是 locator、DOM 结构、class/id、文案锚点、测试 API 或格式变化。修复时可以自动改写定位。
- `EXPECTATION_CHANGE`：测试要验证的业务结果/断言目标本身变了；旧断言还在检查旧行为。修复需要改断言语义，通常要人工/业务确认。
- `SUSPECTED_REGRESSION`：无法排除新版本真的回归；看不出是测试老了还是应用坏了。保守选项，不应自动改写采纳。

### 4.3 决策表

| 你看到的情况 | 填 |
|---|---|
| 只是定位器写法、DOM 层级、class/id、文案锚点、测试 API（`page.$`→`page.locator`）或框架迁移变了；测试想验证的东西没变 | `STRUCTURAL_ONLY` |
| 测试要验证的业务结果/断言目标本身变了；旧断言还在检查旧行为 | `EXPECTATION_CHANGE` |
| commit 像是修 bug/改行为，旧测试失败也可能是真的回归；看不出是测试老了还是应用坏了 | `SUSPECTED_REGRESSION` |
| 测试自身 flaky，只是把定位器改精确，意图不变 | `STRUCTURAL_ONLY` |
| 测试自身的严格化（等待条件细化、选择器收紧、新增 `filter`/`hasText`、改用更精确的 role+name、加 `toHaveCount` 等），但被验证的应用行为/业务结果未变 | `STRUCTURAL_ONLY` |
| 业务对象实质变化（例如 markdown 卡片改成 codeblock 卡片） | `EXPECTATION_CHANGE` |

### 4.4 特别规则

- 仅由测试框架迁移（vitest→Playwright）或定位器 API 迁移（`page.$`→`page.locator`、`waitForSelector`→`locator`）引起 → `STRUCTURAL_ONLY`。
- 测试自身的 flaky 修复：意图不变、仅定位器更精确 → `STRUCTURAL_ONLY`；插入/断言的业务对象实质变化 → `EXPECTATION_CHANGE`。
- 断言语义反转、目标列/目标元素实质改变，且无法确认是否掩盖回归 → 优先 `EXPECTATION_CHANGE` 或 `SUSPECTED_REGRESSION`。
- 看不出是测试过时还是应用真回归 → 保守选 `SUSPECTED_REGRESSION`。
- 如果应用 diff 显示的是纯样式/布局重构，旧断言的业务目标没变 → `STRUCTURAL_ONLY`；如果断言目标跟着业务对象一起变了 → `EXPECTATION_CHANGE`。
- **判据边界（2026-11-08 作者确认）**：测试自身的严格化——等待条件细化、选择器收紧、新增 `filter`/`hasText`、改用更精确的 role+name、增加 `toHaveCount` 等——**不构成 `EXPECTATION_CHANGE`**；只有被验证的应用行为/业务结果改变时才判 `EXPECTATION_CHANGE`。
  - 正例（`rb039` / `rb040` 类）：把“等待任意选中菜单项”改为“等待含 `'snippet'` 的菜单项可见”，但旧测试后续的 `toHaveCount(2)` 等效断言未变 → `STRUCTURAL_ONLY`。
  - 反例（`rb033` 类）：断言对象从 markdown 卡变成 codeblock 卡，业务对象本身变了 → `EXPECTATION_CHANGE`。区分标准是“断言指向的对象/业务结果是否变了”，不是“测试写法是否更严”。
  - **遮蔽不可约边界（`rb033`）**：该条的业务语义恰好由被遮蔽的属性值 `[data-kg-card="codeblock"]` 承载，协议 B 下标注者看不到这个新值，只能判 `STRUCTURAL_ONLY`。这是遮蔽规则的设计性代价，不是脚本错误；论文与指南均须披露，**不得为单条放松通用遮蔽规则**。

> **隔离说明（2026-11-12）**：上面判据边界下的三条举例只用于作者与审阅者理解判据边界，**不随任何盲评材料发放**。盲评包只发放 §4.3 决策表与 §4.4 判据边界主段，不含本节举例。

### 4.5 常见误判

- 把“定位器变了”一律判成 `EXPECTATION_CHANGE`。如果只是写法/结构变化、意图没变，应该是 `STRUCTURAL_ONLY`。
- 把“commit 是 feat”一律判成 `EXPECTATION_CHANGE`。加功能也可能只是结构变化，仍要看旧断言的业务目标是否改变。
- 因为看不出原因就随便选一个。看不出就选 `SUSPECTED_REGRESSION`，这是协议规定的保守选项。
- 看到应用文件列表里有组件文件，就认定业务逻辑变了。文件路径只说明“改了哪里”，不说明“怎么改”；要以应用 diff 为准。
- 把 `EXPECTATION_CHANGE` 和 `SUSPECTED_REGRESSION` 混用：前者是“测试该改”，后者是“可能是应用坏了、先别改”。两者修复政策相反。

### 4.6 填写

- 只填 `STRUCTURAL_ONLY` / `EXPECTATION_CHANGE` / `SUSPECTED_REGRESSION`，全大写、下划线。
- `final` 留空。
- 拿不准时在备注里写“缺应用行为证据”或“断言目标看不出是否变”，不要用备注代替标签。

### 6.4 方案一的遮蔽规则（断言级测试 diff）

作者决定（2026-11-08，方案一）：**只遮机械路径，保留语义锚。**

判定原则：这个字符串说明“断言的对象是什么”就保留，只说明“怎么找到它”就遮蔽。遇到两者混合的表达式（例如 `getByRole('button', { name: 'Snippet' })`），保留 role 与 name，遮蔽其余。

**遮蔽（机械寻址路径）：**

- CSS 选择器与 id/class；
- `data-testid` / `data-*` 的值；
- `nth()` / `first()` / `last()` 索引；
- xpath；
- `page.$` / `page.locator` / `cy.get` 之类的选择器字符串；
- `new_locator` 中的路径片段。

**保留（语义锚）：**

- `getByRole` 的 role 与 name；
- `getByText` / `getByLabel` / `getByPlaceholder` / `getByAltText` / `getByTitle` 的文本；
- `filter({hasText})` 的文本；
- 断言值（`toHaveText` / `toContainText` 等）与 matcher。

**删除：**

- 新测试文件路径、完整新测试；
- 可复制运行的整段新测试脚本；
- 截图、trace、DOM dump 等能显示新定位器的材料。

**遮蔽方式：**

- 把机械寻址参数替换为 `<LOCATOR_REDACTED>`，保留定位 API 名称与语义参数，不要只删整行导致断言无法理解；
- 若 `-`/`+` 行只因机械寻址不同而完全一样，新增侧标为 `<LOCATOR_CHANGED>`：说明“路径变了”，但不显示新路径；
- 不要用“近似遮蔽”：机械路径只要还能还原，就算泄露。

**遮蔽必须验证不可还原，验证步骤：**

1. 对每条 `new_locator` 的**机械寻址片段**，在遮蔽后的断言级测试 diff 中做精确匹配、空白归一化匹配与 token 检查；命中数必须为 0。
2. 若某机械片段与 `old_locator` / 旧测试块中的字符串相同，它属于按协议已披露的旧定位器，单独记录，不计为“新定位器泄露”。
3. 搜索新测试文件路径和若干新增非断言行；命中数必须为 0。
4. 语义锚允许出现，但必须在 `redaction_verification.md` 的“按协议允许可见的语义锚”一节逐条列出类型、值、出现次数与理由，不得笼统放行。
5. 记录遮蔽脚本、输入、输出与重新计算的 `sha256`。

**披露措辞（发放说明中必须写明）：** “遮蔽对象是寻址路径，不是语义锚；因此新定位器中的语义部分对标注者可见。”

**已知不可约边界（rb033）：** `rb033` 的业务语义恰好由被遮蔽的 `[data-kg-card="codeblock"]` 属性值承载。协议 B 下标注者看不到新值，只能判 `STRUCTURAL_ONLY`；A 条件下该条稳定判 `EXPECTATION_CHANGE`。这是通用遮蔽规则的设计性代价，不是遮蔽失败，也不为它放松规则；论文与指南必须同时披露这一点。
