# 可行性验证报告：在真实开源项目上验证两个核心闸门

> 目的：在**真实开源 Playwright 项目**（非自建 demo）上验证课题核心机制是否成立。
> 闸门①：逐用例覆盖能否稳定插桩采到、且归属到原始源码。
> 闸门②：Semantic UI Diff（贡献点 C1）能否从真实 JSX 算出。
> 结论：**两个闸门均通过**，并各自暴露出一个必须在论文中正面处理的工程约束。

日期：2026-06-17｜环境：Node 24.15 / Playwright 1.60 / Chromium / macOS arm64

---

## 1. 实测对象

| 项目 | 技术栈 | 角色 | 结果 |
|---|---|---|---|
| `mxschmitt/playwright-test-coverage` (cand_coverage) | React 19 + Vite + Playwright + vite-plugin-istanbul | 闸门①②主验证对象 | ✅ 可用 |
| `debs-obrien/playwright-movies-app` (cand_movies) | Next.js 16 + React 19 + Redux | "重型真实项目"参照 | ⚠️ 需大量改造，暂不可用 |

---

## 2. 闸门①：逐用例覆盖插桩 —— 通过 ✅

`cand_coverage` 用 `vite-plugin-istanbul` 在 dev server 插桩，配 fixture 在每个测试上下文关闭时 dump `window.__coverage__`。实测：

- 全量 3 个测试本地全绿；逐用例覆盖成功落盘到 `.nyc_output`。
- 覆盖**以原始源码路径为键**（`src/App.tsx`、`src/index.tsx`），含 statement(`s`)/function(`f`)/statementMap/fnMap。
- **逐用例可区分**：点击 Red / 点击 Turquoise / 默认 三个用例执行到的语句、函数集合各不相同——证明可做到比文件级更细的归属。

**关键约束（必须在论文中处理）**：`vite-plugin-istanbul` 报告的行号位于 **JSX 转译后的代码空间**（`App.tsx` 实际 42 行，覆盖里 statement 行号到 134）。
- **文件级（L1）归属干净**，不需要任何映射；
- **子文件级（语句/行，L2/L3）必须经 sourcemap 反映射**才能把"diff 的原始源码行"对上"覆盖的转译行"。本项目已开 `build.sourcemap:true`，具备反映射条件，但这一步要在实现里显式做，不能假设行号一致。

## 3. 闸门②：Semantic UI Diff from real JSX —— 通过 ✅

用 TypeScript 编译器 API 解析真实 `App.tsx`，抽取语义 UI 节点并对"改造后版本"做差异：

- 正确抽出 `<a>Learn React` + 3 个 `<button>`（含 text、onClick handler、行号）。
- 对 old→new 差异，正确产出：
  - `MODIFY`：`<a>` 的 href `reactjs.org → react.dev`；Turquoise 按钮新增 `data-testid`（靠"同 tag+同 handler"结构匹配关联上）。
  - `ADD`：新增 Crimson、Green 按钮。
  - `REMOVE`：移除 Red 按钮。

**关键局限（必须在论文中处理）**：当一个节点的**文本与 handler 同时改变**（Red→Crimson 且 handleMakeRed→handlePaintCrimson），所有稳定身份信号都变了，静态结构匹配无法把它识别为一次 `MODIFY`，退化成 `REMOVE + ADD`。
- 影响：会把"改名"误判为"删一个+加一个"，可能多触发一次生成、漏掉一次精准修复。
- 对策（写进方法）：补**运行时 DOM 位置/邻域匹配**（同路由、同父容器、同序位）与 base/head DOM snapshot 对照，做二次消歧——正好是 C1 设计里"静态 UI AST diff + 运行时 UI diff"互补的理由。

## 4. RQ1 在真实代码上的闭环（locator 驱动，免 sourcemap）

把上面的 Semantic UI Diff 关联到真实测试的 locator（`USES_LOCATOR` 信号），一次性给出选择 + 修复 + 生成触发：

```
selected_for_rerun: ["App.test.ts"]            # 含 page.click("text=Red")，被正确选中
repair_triggers:    removed "Red" -> 候选 "Crimson"   # 失效 locator + 修复候选
generation_gaps:    新增 "Crimson"、"Green" 无测试触达 # 生成目标
未选中:             App2.test.ts(Turquoise)            # 与本次变更无关，正确排除
```

意义：除了基于覆盖的选择（主线），**UI 签名 ↔ 测试 locator 匹配是第二条、且对 E2E 更自然的选择信号**——它不依赖覆盖 sourcemap，并能同时驱动修复与生成。建议作为覆盖信号的补充写进方法。

> 诚实说明：本轮 RQ1 用的是在真实文件上**合成的一次代表性 UI 变更**，尚未做"真实 git 历史 commit 的 V_old→V_new replay"。后者需要一个满足下节条件的**多文件**真实项目，是下一阶段工作。

## 5. 适配 / 不适配项目特征（来自实测）

**适配（可低成本跑通）**：本地起服 + 源码未压缩可插桩（vite-plugin-istanbul / babel-plugin-istanbul）+ 测试打本地实例 + 无强外部依赖。

**不适配 / 需重改造**（以 `cand_movies` 为例）：
- 应用源码是 **git submodule**，浅克隆下根本没拉到（`find *.tsx` = 0）；
- 配置**硬性要求 auth 凭据**（`MOVIES_USERNAME/PASSWORD`）且依赖**外部影视 API** → 易 flaky/被墙；
- **无任何覆盖接线**，要自行往 Next build 注入 istanbul；
- Next SSR 多进程，`window.__coverage__` 采集更复杂。
→ 归入"需大量工程改造"类，作为数据集构造时的排除/降级样本。

## 6. 对论文方向的结论

- **两个核心闸门在真实代码上都立得住**：覆盖可逐用例插桩并归属源码；Semantic UI Diff 可从真实 JSX 算出，并能驱动选择/修复/生成闭环。
- **C1（Code Diff → Semantic UI Diff）经得起真实数据检验**，且暴露的两个约束（转译行需 sourcemap、改名退化为增删）恰好对应"静态+运行时互补"的方法设计，是可写进论文的真实问题而非空想。
- **下一步（多文件 RQ1 commit replay）**：寻找满足第 5 节"适配"条件、且 **commit 历史含 UI/路由/组件变更的多文件真实项目**，跑 20–30 个 commit 的小样本，输出文件级 Reduction/Safety/Precision（先 L1，再用 sourcemap 上 L2/L3）。

## 7. 复现命令

```bash
# 闸门①：真实仓库逐用例覆盖
cd diffe2e/real/cand_coverage && npm i && npx playwright install chromium && npx playwright test   # -> .nyc_output

# 逐用例打标签 + 查看 statement 级归属
node ../analyze.mjs --show --cov cand_coverage/cov_pertest --file src/App.tsx

# 闸门②：真实 JSX 语义 UI 差异
cd diffe2e/real
node uidiff.mjs extract cand_coverage/src/App.tsx
node uidiff.mjs diff _uidiff_fixtures/App.old.tsx _uidiff_fixtures/App.new.tsx

# RQ1 闭环（UI diff -> 选择/修复/生成）
node uidiff.mjs diff _uidiff_fixtures/App.old.tsx _uidiff_fixtures/App.new.tsx > _uidiff_fixtures/diff.json
node link.mjs _uidiff_fixtures/diff.json cand_coverage/e2e
```
