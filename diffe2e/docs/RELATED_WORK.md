# 相关工作：两维定位与技术缺口

> 本文回应评审意见 #5（相关工作偏粗）。按导师指出的两个关注点构造区分维度——**(A) 代码变更感知**（要求定向分析与生成）、**(B) 浏览器端到端测试**（区别于单元/集成等局部测试，需全局上下文：页面/路由/DOM/定位器）——把现有工作分族、逐篇标注、指出技术层面不足，并引出本方法。文献编号沿用进展汇报参考文献表。

## 1. 两维分析框架

- **维度 A：代码变更感知程度**
  - `A0` 无：与具体 diff 无关（泛化生成/通用修复）。
  - `A1` 粗粒度：文件/方法级变更影响分析（经典 RTS）。
  - `A2` 细粒度定向：以 diff 为核心输入，定向分析**并**定向生成/修复针对变更的测试。
- **维度 B：测试层级与上下文**
  - `B0` 局部：单元/集成测试，源码内可定位的上下文。
  - `B1` 全局：浏览器 E2E，跨越源码↔路由↔DOM↔定位器↔断言的全局上下文。

> 本方法目标点 = **(A2, B1)**：代码变更感知 + 浏览器端到端全局上下文。下面说明现有工作几乎都落在其他象限，留下该象限的空白。

## 3. 技术层面的共同不足 → 引出本方法

综合三族，现有工作在目标象限 **(A2, B1)** 留下三个技术缺口：

1. **缺源码↔浏览器的语义桥**：单元 RTS/修复（[1][19][20][24]）的覆盖/依赖映射止于源码层，无法把一次 diff 对应到 DOM/定位器/断言；E2E 生成/修复（[6][7][9][12][16]）又不以 diff 为核心。→ 本方法用 **Semantic UI Diff + 测试↔代码映射器**（`MAPPER.md`）显式建立该桥。
2. **缺可证明的召回保证**：RTS 工作多报经验 Safety，但 E2E 场景下缺少"与选择器无关"的真值定义与安全性论证，且**未处理副作用经共享状态的间接影响**。→ 本方法给出条件安全命题 + 非循环结果差异 oracle + 状态依赖闭包（`SAFETY.md`）。
3. **缺端到端闭环与净收益量化**：现有工作多为单点（选择 或 生成 或 修复），且少有"选择开销 + 执行时间 vs 全量"的净收益与资源量化。→ 本方法把选择→运行/修复→缺口→生成串成代码变更感知闭环，并以净收益模型量化（`COST_MODEL.md`）。

## 4. 一句话定位

> 现有工作要么"变更感知但停在单元层"（A2,B0：[1][3][49][50][51][52]），要么"做浏览器 E2E 但与变更无关"（A0,B1：[6][7][9][12][16]）。本方法填补 **(A2, B1)** 空白：**代码变更感知的 Web 应用端到端回归测试用例选择与生成**，以测试↔代码映射器与 Semantic UI Diff 为桥，给出可证明的召回保证与净收益量化，且工具无关（Playwright 仅为实现实例）。
